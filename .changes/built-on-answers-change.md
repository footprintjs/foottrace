- `causalChain` and `sliceForKey` can return a result that holds a cycle. When a stage commits a key between two commits of another stage that both add to that key, each of the two rests on the other, and the result holds an edge each way. It was always a DAG before. `flattenCausalDAG`, `formatCausalChain`, `sliceToJSON` and `formatSlice` visit a node once and end on such a result. Code that follows `parents` or `parentEdges` itself must remember the nodes it has visited, or it does not end. The cause graph has one node per commit and stays acyclic.
- `explain` (`foottrace/cause`) answers differently for one kind of record: a `set` row the writer built on a stage's view, where that view held no write of the key (the usual case: a key no earlier commit wrote, which one stage merges into and also writes inside, under `commitValues: 'delta'`). Without exact read sources, the node of that row now carries the gap `untracked-input`, so `explain` through it is `incomplete`, names no root cause, and lists the stage among the alternatives. For the same run 1.13.0 confirmed that stage as the root cause and called the answer `complete`. That was wrong: part of the value came from before the run, which no commit holds. A caller that branches on `confidence` or `rootCause` sees the difference. A record written before 1.14.0 carries no such row, so this does not reach it; with exact read sources (`RecordScope.readSources`) the state before the run is a known end of the walk and no gap is added.
- The sentence of `'nested-rows'` in `HONESTY_CODES`, and the `'nested-rows'` note of `sliceForKey`, `forwardSliceForKey` and `keyTimeline`, say that earlier writes account for the rest of the value and that a walk back follows them. They said the earlier writes "may account for the rest". The code is unchanged; the words changed because the walk now does follow them.
